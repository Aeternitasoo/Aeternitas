## 冻结案例与执行边界

`evals/m6/protocol.json` 先声明验收规则，开发与留出分别保存 manifest 和每例文件 SHA-256。`evaluation_cases.py` 调用实际业务函数，记录预期结果、实际结果、业务拒绝原因和独立 artifact。JSON 格式正确并非唯一通过条件。

开发集有 8 个案例、23 个相关业务场景，覆盖 AAPL / MSFT、披露截止日、缺失与零值及亏损、冲突、财务期间与币种、引用集合、逐字摘录、数值表达、新闻范围和外部失败。公共 SEC 材料是从已验证原始快照裁剪的精确观测，保留原快照 hash、原 JSON pointer 和逐条观测映射；这是离线重放，不是新获取的数据。其余受控材料明确标为 synthetic。

```bash
.venv/bin/python scripts/evaluate_m6.py --split development
.venv/bin/python -m pytest -q test_m6_evaluations.py
```

结果写到 `data/live/m6/development-result.json` 与 `development-cases/`。案例字节与冻结 manifest 不一致会被拒绝；程序自身异常不能冒充预期的业务拒绝。普通 pytest 只执行开发集，不自动发现或运行留出目录。

4 个留出案例由另一位代理创建与冻结，开发实现者不查看其输入或目标答案。只有开发、实现与复核记录冻结后才执行留出首跑，保存首跑 ledger、原始结果和实现指纹；失败必须保留并解释，修复后另记复测，不能改写首次结果。`--split holdout` 是最后阶段的显式入口，不用于开发时反复调参。

本次留出首跑为 4 个案例、8 个相关场景，全部硬规则通过，真实来源与模型调用均为零；109 份冻结文件在执行前后保持一致。首跑结果与 ledger 已保存，开发实现者没有读取留出输入或答案。这是本项目冻结回归的结果，不是对证券研究准确率的估计。

通过 12 个小型项目案例不能换算为全市场准确率。测试数量、场景数量和模块验收环节分别记录。

## 自动规则与人工判断

程序可以检查公司、披露时间、Decimal 财务计算、证据身份、引用集合、原文子串和失败状态。它不能判断一段原文是否充分支持结论含义。语义无关的论点即使带有合法逐字引用，仍须保持 `human_review_required`，不能标为已经获得来源支持。

本次人工来源复核按公司至少抽查 3 条重要论点。`data/live/m6/source-campaign.json` 记录 AAPL / MSFT 原报告、原来源位置、判断理由、12 个财务值的原 JSON / PostgreSQL NUMERIC / inline XBRL 对照，以及有界的可比性复核。比较报表中的期间、币种、合并口径与六个值已定位；另读部分会计政策及税项 / 非经营项目说明。只能支持“按当时披露的历史 GAAP 值比较”，不能据此证明净利率变化全由主营效率造成，也不代表完成全部会计政策或公司事件审计。

这些额外完整财报段落用于助手来源复核，没有追加到已冻结的模型证据。模型注明“当前给定片段缺少税项解释”，应按其实际输入范围判断。助手复核与用户独立验收分开记录，不使用另一个 LLM 的评分自证正确。

受控来源更新另用 MockTransport 驱动实际采集器和隔离 PostgreSQL schema，检查缓存、强制更新、未来披露与次日新闻排除、旧数据保留、重复导入、坏字段及覆盖不足。该过程没有真实模型或来源请求，不能计作新的 live 成功。

## 新 prompt 的角色范围

新研究使用 `evidence-roles-m6-v1` 和各角色的 `*-m6-v1` prompt，文件位于 `prompts/m6/`。结果 schema 仍为 `analyst-result-m4-v1`，报告 schema 仍为 `aeternitas-report-m4-v1`。原 `prompts/m4/` 与历史报告不改写，旧报告继续按原版本校验。

基本面角色只看财务事实、程序计算和申报片段；事件角色只看本次新闻摘要。风险及综合收到 `input_evidence_scope` 和 `prior_analysis_scopes`：某前序角色“没有收到新闻”只描述该角色的输入，不能推成整次研究没有新闻。范围元数据和提示约束旨在修复 M5 抽查中发现的一处范围误读，不能保证模型不会再误解；重要论点仍需原文抽查。

## 真实模型对照与原失败

`m6_comparison.py` 与 `scripts/compare_m6.py` 使用同一份已审计的冻结来源、公司、日期、问题、账号模型和综合证据包。直接综合使用相同综合指令与输出契约，前序分析为空；角色流程保留基本面、事件、风险、综合四步。每一侧上限均为 8 次请求和 1800 秒；直接综合至多两次（含一次校验修复），原试验总上限 10 次。预算是上限，不会为凑相同次数而消耗剩余额度。

原试验位于 `data/live/m6/comparison/`，累计 7 次真实模型请求后停止：直接综合两次完成，角色流程五次请求，风险角色已用完两次尝试，仍未完成。两次网络请求的实际结果 / 额度消耗不明，保留原状态与诊断，费用为 `unknown`；不能记作零。直接综合中的一次重复引用被校验拒绝，修复后结果保存。

在保留原失败的前提下，只另行声明一次新的正式角色任务，最多 8 次请求、1800 秒；原直接综合的产物逐字节复用，不再发送直接综合请求。全程实际累计上限为原 7 次加新角色最多 8 次，即最多 15 次；不能把复用的直接综合两次重复计数。`data/live/m6/replication.json` 的排他创建阻止该声明再次启动新的复验。新任务也失败时，保留失败并把比较标为待完成，不能继续无限新建试验。

新角色任务通过 M5 的合法输入检查点、owner 交接与原绝对 deadline 执行，输入准备不调用模型或来源接口。使用同一冻结证据不会冒充新 SEC / 新闻请求。完成后产物位于 `data/live/m6/comparison-replication/`，正式 run 仍可通过 `report RUN_ID` 与 `verify RUN_ID` 回查。
